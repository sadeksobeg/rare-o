## 3. Findings by severity

### Critical

**C-1. Brokerage photos are served to anyone with the URL — zero authentication.**
`public/uploads/brokerage/{requestId}/{file}.webp` sits under Next.js's static `public/` directory. There is no middleware rule, no route handler, and no `next.config` rewrite covering `/uploads/*` — confirmed by grep (no match in `middleware.ts` or `next.config.*`) and confirmed live: I generated one real file through the actual `saveBrokeragePhotos()` function, started the real dev server, opened a **brand-new browser tab with zero cookies**, and fetched the file directly.
```
GET http://localhost:3001/uploads/brokerage/audit-probe-req/1793316381873-1f27606ea70f.webp → 200 OK
```
The image rendered in the tab. Filenames are unguessable in practice (cuid request id + random hex), so this is not a *browsable* leak, but it is a real one: any URL that reaches a screenshot, a forwarded message, a browser history sync, a referrer header, or server/proxy access log exposes a trader's private goods/deal photos to anyone who has it, logged in or not. This is exactly the exposure the owner named.
Probe artifacts (file, directory) were deleted immediately after the test; nothing was left behind.

**C-2. "Forced password change at next sign-in" does not exist in the real app.**
Searched the full codebase for `mustChangePassword`, `forceChange`, `requirePasswordChange`, `passwordChangeRequired` (case-insensitive) — zero matches, anywhere. Checked `TraderAccount` in `prisma/schema.prisma` directly for any such flag field — none exists (`id, email, passwordHash, displayName, companyName, phone, status, adminNotes, interestCategorySlugs, interestNotes, ...` — no password-state field at all). The admin-reset / show-once-temp-password half of the owner's security correction is real (`trader-forms.tsx`), but the half that makes it actually safe — the trader being *forced* to replace that temp password before doing anything else — was only ever built as a non-functional mockup screen in design-lab (`/force-password-change`, a static form with `router.push("/trader")` on submit, no backend check). Today, a trader who never changes their reset password can keep using it indefinitely.

### High

**H-1. Migration history is out of sync with the live database — `prisma migrate deploy` will fail here.**
```
$ npx prisma migrate status
Following migration have not yet been applied:
20261029160000_brokerage_request_photos
```
But:
```sql
-- live DB, \d "BrokerageRequest"
photoPaths | text | not null | '[]'::text   ← column already exists
```
and `_prisma_migrations` (the table Prisma itself uses to track what's actually been run) has only 4 rows, stopping at `20261029115019_brokerage_domain` — the `photoPaths` migration was never recorded as applied here, even though its column is live. This is the exact "migrate vs push" ambiguity the owner flagged, now evidenced: the `photoPaths` column was added via `prisma db push` (or equivalent raw DDL) directly against this database, and a migration *file* matching that change was created afterward, but `prisma migrate dev`/`resolve` was never run to reconcile the two. If `prisma migrate deploy` is ever run against a database in this exact state (which is the state Cursor left this machine in), it will attempt `ALTER TABLE "BrokerageRequest" ADD COLUMN "photoPaths" ...` against a table that already has that column, and fail. The migration SQL itself is additive-only (`ADD COLUMN ... DEFAULT '[]'`, no drops) and poses no data-loss risk on its own — the risk is entirely the broken deploy, not the schema change's content.

**H-2. Nothing from this porting work is committed.**
`git rev-parse feat/port-lab-to-real` and `git rev-parse ui/mockups-rebuild-v2` return the **identical** commit (`a77d96a`). Every file Cursor touched — 31 modified tracked files, 23 new untracked paths, two migration folders — exists only as uncommitted working-tree state. `git stash list` is empty, so there is no safety net; a `git checkout`, a crashed editor's "discard changes," or simply working in a different session/branch would silently lose all of it. This is worth fixing before anything else, independent of whatever else this audit finds.

### Medium

**M-1. Admin sidebar content isn't wrapped in a landmark (axe: `region`).**
Re-ran the axe check on design-lab with a fully pre-warmed server (every route hit once before testing, to rule out compile-lag false positives like the ones I second-guessed at the end of last session). The violation is real and reproducible: every flagged node — the brand link, each `SidebarGroupLabel`, every nav link's text — sits inside shadcn's `Sidebar` primitive, which doesn't emit a `<nav>` or `role="navigation"` wrapper around its content. Confirmed by extracting the exact flagged selectors via Playwright + the project's own pinned `axe-core` (4.13.0) rather than trusting a one-off browser check (an earlier same-day check via a different, older CDN axe version had shown zero violations — a real version/method mismatch, not evidence the bug was fixed). This is a design-lab-only finding (not yet ported to the real app, which has its own, differently-structured admin shell not checked for this specific issue in this pass).

**M-2. BROKERAGE-SPEC.md is thinner than VISION.md §7.4 asked for.**
VISION.md explicitly lists "dictionary keys AR/EN" as a required section of this spec file. The actual file (26 lines) covers models, lifecycle, permissions, and routes, but has no dictionary-key section at all — someone reading only the spec can't see what i18n keys the brokerage feature expects to exist.

**M-3. Two "orphan" components exist for features the report implies are live.**
`components/admin/dashboard-domain-chart.tsx` (a real `recharts`-based donut, matching design-lab's domain-split chart) and `components/brand/logo-scene.tsx` (a real Three.js/R3F logo) are both fully written but imported by nothing — confirmed by grep across `app/`/`components/`. The live admin dashboard currently shows the domain split as a plain horizontal bar list, not the chart component that exists in the repo; the live login page uses `logo-scene-mount.tsx` (pure CSS rings), not `logo-scene.tsx`. Neither is a regression — the CSS-rings login mark is a documented, deliberate choice ("R3F crashing after hydration" per the component's own comment) — but it does mean "recharts and three are in the app" is a half-true statement without noting that the components built against them aren't wired to anything yet.

### Low

**L-1. Twelve leftover test rows in the local brokerage table.**
`scripts/brokerage-lifecycle-e2e.ts` doesn't clean up after itself; each run leaves 4 rows (`"E2E وساطة — ..."`) in `BrokerageRequest`. I found 12 (three accumulated runs, one of them mine from this audit). Not destructive, just dev-DB hygiene — flagging rather than deleting, since that's a write action outside this audit's scope.

**L-2. `CANCELLED` terminal state untested.**
See claim #7 above — the e2e script covers DECLINED and REJECTED but not CANCELLED. `canAdminTransition`/`canTraderTransition` both list CANCELLED as a valid target from several states, so the transition logic itself supports it; it's just never been exercised by a test.

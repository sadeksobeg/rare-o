# تقرير التسليم — الجولة الثانية (تنفيذ مطابق للمرجع البصري)

**الفرع:** `ui/pilot-world-class` · **التاريخ:** 2026-11-08

> تسليم واحد ثم توقف (البند 8 من الموجز). لا انتقال لأي صفحة أخرى دون موافقة كتابية صريحة.

## ⚠️ ملاحظة حرجة عاجلة — ليست من عملي، لكن يجب الانتباه إليها فوراً

أثناء التحقق النهائي، فحصتُ `.env` المحلي (كما يطلب الموجز دائماً) ووجدت
`WHATSAPP_CONNECT_ON_START=true` و`WHATSAPP_OUTBOUND_ENABLED=true` — أي **مفعَّلتان**،
مخالفتين للقيد الذي لا يُلغى أبداً في كل موجز وصلني. تحقَّقتُ من تاريخ تعديل الملف:
**31 أكتوبر 2026، الساعة 17:51** — أي قبل أي عمل لي في هذه المحادثة أو الجولة السابقة
بأيام، فهذا **ليس تغييراً مني ولا نتيجة لأي أمر نفّذته هنا**. لم أُعدّل `.env` إطلاقاً.
شغّلتُ خادم إنتاج حقيقي (`next start`) للتحقق من هذه الجولة، وسجلات الخادم لا تُظهر أي
محاولة اتصال واتساب فعلية (عامل واتساب `worker:whatsapp` عملية منفصلة لم أُشغّلها)، فلا
دليل على اتصال حقيقي أو مسح QR حدث أثناء عملي. **لكن القيمتين تبقيان مفعَّلتين في الملف
نفسه الآن**، وهذا يستحق انتباهك المباشر بغض النظر عن مصير هذه الجولة — لم ألمسه ولن ألمسه
دون توجيهك الصريح.

## 0) الفرق عن الجولة الأولى

الجولة الأولى رُفضت لأنها رقّعت المكوّنات القديمة بتجاوزات CSS فوق `globals.css` بدل
إعادة بناء حقيقية. هذه الجولة **حذفت** كل تلك التجاوزات والبنية القديمة فعلاً
(18 ملف مكوّن قديم حُذف بالكامل — القائمة في §4) وبَنَت قشرة ولوحة تحكم جديدتين من الصفر،
تطابقان `docs/ui/reference/admin-dashboard/index.html` (نسخة المالك المحفوظة محلياً من
`rareoud-admin-dashboard-reference.zip`) بنيةً وحركةً وألواناً — القيم المنسوخة منه حرفياً،
لا بتقدير بصري.

## 1) ما بُني

### أ) نظام الرموز
`styles/tokens.css` — مقياس `--rad-*` جديد منسوخ حرفياً من متغيرات CSS في المرجع
(`--c0`, `--surface`, `--tx`, `--ac`, `--sb*`...) لكلا الوضعين الداكن والفاتح، ضمن
`.ro-portal[data-portal="admin"]`. لا تداخل مع `--pilot-*` (الجولة الأولى) — ذلك المقياس
بالكامل أُزيل من كل تجاوزات `globals.css` (4 كتل "PILOT override" حُذفت).

### ب) CSS بنيوي مخصص
`styles/admin-dashboard.css` (ملف جديد مستقل، ~1300 سطر) — منفذ شبه حرفي لـ CSS المرجع
(أسماء الأصناف بادئة `rad-` لتفادي أي تصادم مع `.ro-portal-*` القديمة)، مستهلِك لمتغيرات
`--rad-*` فقط — لا hex خارج `styles/tokens.css` (تحقَّق آلياً، راجع §6).

### ج) مكوّنات React نظيفة (`components/admin/rad/`)
`sidebar.tsx` (قائمة بمجموعات، مؤشر نشط 3px، طيّ+تلميحات، تذييل بطاقة المستخدم)،
`topbar.tsx` (مسار تنقل، زر بحث يفتح الباليت، إشعارات/واتساب/مظهر/لغة)،
`command-palette.tsx` (overlay حقيقي، Ctrl+K، تنقل بالأسهم، بحث فعلي عبر
`/api/admin/command-search` الموجود مسبقاً + مجموعة إجراءات سريعة)، `kpi-card.tsx`
(عدّاد تصاعدي، شارة دلتا bidi-آمنة، مصغّر فقط عند ≥7 نقاط حقيقية، حالة "لا شيء بانتظارك")،
`action-queue.tsx` (تبويبات مُجزّأة بمؤشر منزلق، صفوف بشارات حالة، تذييل عدّ، حالة فارغة)،
`orders-chart.tsx` (رسم أعمدة SVG مرسوم يدوياً — لا مكتبة رسوم، محاور وقيم حقيقية، تلميح
تمرير، مبدّل نطاق 7/14/30، جدول `sr-only` بديل لقارئ الشاشة)، `whatsapp-card.tsx`،
`activity-timeline.tsx`، `mobile-tabbar.tsx`، `shell-client.tsx` (الحالة التفاعلية: طيّ،
درج الجوال، الباليت).

### د) بيانات حقيقية بالكامل
`app/admin/(protected)/page.tsx` يستهلك `getAdminHomeData()` الموجودة مسبقاً دون تعديل
منطقها — فقط `getRequestsTrend(14)` → `getRequestsTrend(30)` لدعم مبدّل النطاق 7/14/30 بجلب
واحد بدل ثلاثة (`lib/admin/dashboard.ts`). كل رقم ومرجع وتاريخ في الشاشة من قاعدة البيانات
الحقيقية — لا بيانات تجريبية من المرجع بقيت في الشيفرة النهائية.

### هـ) الصياغة العربية
مفاتيح قاموس جديدة كاملة (`dict.ad2`، نوع + عربي + إنجليزي) بدل إعادة استخدام مفاتيح
`admin`/`adminUi` المشتركة مع صفحات أخرى (تفادياً لأي أثر جانبي على صفحات خارج النطاق).
الجمع النحوي العربي الصحيح (مفرد/مثنى/جمع قلة/جمع كثرة) عبر `lib/i18n/plural.ts` الموجودة
مسبقاً (`Intl.PluralRules`) لعنوان "19 أمراً بانتظارك"، ووصف واتساب، وتسمية الرسم، وعدد
القطع في صفوف قائمة الانتظار — لا "1 أمور" بعد الآن.

### و) حركة
دخول متتابع (`--rad-s` + `rise`)، عدّاد تصاعدي للأرقام، نمو أعمدة الرسم، مؤشر تبويب منزلق
(JS-measured)، ظهور صفوف متدرّج، نبضة نقطة حالة واتساب، فتح/إغلاق الباليت، تموّج ضغط
الأزرار — كلها `transform`/`opacity` فقط، لا `transition: all` (تحقَّق آلياً)،
`prefers-reduced-motion` يُصفّر كل مدد الحركة (قاعدة CSS عامة في `admin-dashboard.css`).

## 2) أخطاء حقيقية وُجدت وأُصلحت أثناء البناء (لا بالتخطيط المسبق)

1. **تحطّم كامل عند أول تشغيل حقيقي:** تمرير دوال (`rangeLabel`/`captionFor`) كخصائص من
   مكوّن خادم (صفحة) إلى مكوّن عميل (`RadOrdersChart`) — ممنوع في Next.js App Router.
   أُصلح بنقل منطق الصياغة (`plural()`) إلى داخل المكوّن نفسه، وتمرير بيانات قابلة
   للتسلسل (قوالب نصية + كائن أشكال الجمع) بدل دوال.
2. **القشرة بلا ألوان إطلاقاً بعد الإصلاح أعلاه:** نسيتُ تغليف `RadShellClient` بموفّر
   السمة (`PortalThemeProvider`) عند إعادة كتابة `shell.tsx` — فاختفى `data-theme`/
   `data-portal="admin"` من DOM بالكامل، فانهارت كل متغيرات `--rad-*` إلى undefined
   (ظهرت الصفحة بلا خلفيات ولا حدود ولا ألوان). أُصلح بتغليف `RadShellClient` بـ
   `<PortalThemeProvider defaultTheme="dark" dataPortal="admin" className="contents ro-portal">`.
3. **خطأ بناء (`next build`) حقيقي:** زر "إنشاء" في ترويسة الصفحة كان `<a>` خام بدل
   `next/link` → فشل قاعدة `@next/next/no-html-link-for-pages`. أُصلح باستبداله بـ `Link`.
4. **فشل تباين لوني حقيقي رصده axe على كل صفحة إدارة (لا AD-02 فقط):** نسخت قيمة
   `--sb-tx3` من المرجع حرفياً (`rgba(244,231,216,.45)`) لتسميات مجموعات الشريط
   الجانبي — تباينها الفعلي 3.91:1 (أقل من حد WCAG AA للنص العادي 4.5:1)، وتظهر في
   كل صفحة إدارة لأن الشريط الجانبي جزء من القشرة المشتركة. رُفعت إلى `.55`
   (5.33:1) — انحراف متعمَّد وموثَّق عن القيمة الحرفية للمرجع لأن الوصول مُقدَّم دائماً،
   كما ينص الموجز نفسه.
5. **hex خارج ملف الرموز:** ستة مواضع hex خام تسلّلت إلى `styles/admin-dashboard.css`
   أثناء نقل CSS المرجع (`#d9bef5`, `#32104f`, `#fff`×2, `#000`×3) — نُقلت جميعها إلى
   متغيرات جديدة في `styles/tokens.css` (`--rad-nb-text`, `--rad-plum-700`, `--rad-white`,
   `--rad-black`). تحقَّق آلي بعد النقل: صفر hex متبقٍ.

## 6) قرار منطق `lib/offers/service.ts` (مطلوب شرحه منفصلاً)

**لم يُفصَل في commit منفصل فعلياً** — كان جزءاً من commit الجولة الأولى الشامل (`f2e8186`)
قبل أن يصل موجز الجولة الثانية الذي طلب الفصل. هذا إقرار صادق بتجاوز هذه النقطة، لا تبرير
لها. **الشرح المطلوب بالأدلة:**

الحالتان `awaiting_payment` و`payment_confirmed` **لا تعنيان دفعاً إلكترونياً عبر المنصة**.
الدليل من `lib/deals/service.ts:341-368`:
```ts
/** Admin confirms offline payment; closes the payment-first deal path. */
export async function confirmDealPayment(input: { dealId: string; adminId: string }) {
  ...
  if (deal.status !== "awaiting_payment") throw new Error("INVALID_STATUS");
  ... status: "payment_confirmed", paymentConfirmedAt: new Date(),
      paymentConfirmedByAdminId: input.adminId, ...
}
```
هذه حالة لمسار "الدفع أولاً" حيث يحوّل التاجر المبلغ **خارج المنصة** (تحويل بنكي/نقدي
منسَّق عبر واتساب عادة)، ثم **الإدارة يدوياً** (`paymentConfirmedByAdminId`) تؤكد الاستلام.
لا بوابة دفع، لا معالجة بطاقات، لا Stripe/PayPal — فقط تتبّع حالة لعملية أوف-لاين. بوابة
نشر العروض في `lib/offers/service.ts` كانت ترفض نشر عرض لصفقة انتقلت بنجاح عبر هذا المسار
الحقيقي الكامل لأنها لم تعد تستقر عند `"accepted"` الحرفية — إصلاح منطقي صحيح، لكن توقيته
(ضمن commit بصري) يخالف تعليمات الموجز الصريحة.

## 7) الفجوات المتبقية (صدقاً)

- **بوابة المطابقة بالصور غير مكتملة** (4 من 8 تركيبات، لا فرق بكسل آلي) — §4.
- **`/dev/pilot` (fixture بيانات غنية) لم يُبنَ** — لم تُختبر حالة "بيانات غنية" إطلاقاً،
  لا بصرياً ولا في بوابة المطابقة.
- **الفحص الآلي لعبارات التطوير** لم يكن سكربتاً حقيقياً، بحث يدوي فقط.
- **`/admin/products` و`/admin/profile`**: المشاكل المرصودة في الجولة الأولى (axe) ما
  زالت قائمة كما هي — مسجَّلة، لم تُفحص ولم تُصلَح هذه الجولة (خارج النطاق فعلاً، لكن
  `/admin/profile` تحديداً زادت فيها فجوة بنيوية `dl/dt/dd` لم تكن مرصودة سابقاً بنفس
  الوضوح — راجع §QA الخام في `AXE-RESULTS.json`).
- **لم يُشغَّل Lighthouse إلا بعد كتابة هذا التقرير إن وصلت النتيجة في الوقت** — راجع
  الجدول أعلاه للنتيجة الفعلية أو غيابها.
- **لوحة المفاتيح**: لم تُختبر دورة تنقل كاملة يدوياً (Tab عبر الشريط الجانبي → الترويسة
  → الباليت → البطاقات) بشكل منهجي — axe يغطي البنية الثابتة لا تسلسل التنقّل الفعلي.
